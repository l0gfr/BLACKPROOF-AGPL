# BLACKPROOF ProofPack Format

The ProofPack Master is the complete internal evidence dossier generated by BLACKPROOF. It is not a third-party delivery artifact.

External transmission uses a distinct ProofPack Delivery built from an explicit whitelist and final user confirmation.

Delivery v5 generates a fresh random `deliveryId` and transmission-scoped public IDs for the case, questions and evidence. Internal Master IDs and the Master fingerprint are not exported, so two recipients cannot correlate deliveries through those technical identifiers. It declares its method version, public schema version and URL, plus a machine-readable verification profile. That profile verifies structural integrity only; it does not authenticate issuer identity, declaration truth, legal validity or a trusted timestamp. Legacy Delivery v1/v2/v3 and the frozen pre-registry V4 contract remain verifiable.

Question `category` and `criticality` remain optional schema properties for backward compatibility, but BLACKPROOF omits them by default from newly generated Deliveries. They are internal BLACKPROOF qualifications, not classifications supplied by the recipient.

## proofpack.json

Machine-readable representation of the dossier.

It contains:

- a Master format version (`formatVersion`)
- an immutable schema version (`schemaVersion`)
- case metadata
- a stable ProofPack identity (`id`) and a unique revision identity (`revisionId`)
- questions
- mapped requirements
- evidence items
- proof debts
- summary
- method version
- generated date
- SHA-256 fingerprint
- the internal Delivery receipt history, when transmissions have been generated

The stable ProofPack ID identifies the evolving structured dossier. Every rebuild receives a new `revisionId`, while the fingerprint covers the exact revision content. Persistent ProofDebt items keep their UUID when their question, optional evidence and debt kind remain semantically unchanged.

## Integrity

The proofpack.json fingerprint lets a recipient check that the content matches the provided fingerprint.

It does not authenticate the author, the truth of declarations or issuer identity, and is not a legal signature.

## Canonical schema validation

New Masters use `formatVersion: blackproof-proofpack-v3` and `schemaVersion: blackproof-proofpack-schema-v3`. The BLACKPROOF method remains independently identified by `methodVersion`.

Immutable public schemas are published at:

- `/schemas/proofpack/v1.schema.json`
- `/schemas/proofpack/v2.schema.json`
- `/schemas/proofpack/v3.schema.json`

V1 and V2 are stored as independent frozen JSON files and protected by committed SHA-256 values. Their published bytes are never regenerated from the current model. V1 accepts historical, unversioned ProofPacks and an absent `sourceQuestionnaire.canonicalizationVersion`; in that case canonicalization v1 is implied. V2 requires explicit format, schema and canonicalization versions, but keeps `revisionId` and `deliveryHistory` optional because that was the published V2 contract.

The same hashes are committed in `packages/core/schemas/SHA256SUMS`, which is
independently retrievable from the GitHub repository. When repository visibility
and plan support GitHub artifact attestations, a separate public-only job attests
the exact downloaded production bundle with narrowly scoped OIDC permissions.
The current private user-owned repository records the verified bundle checksum
and must not describe it as GitHub-attested. A future signed release may add
another trust anchor.

V3 is the current strict contract. It also requires `revisionId` and `deliveryHistory`. Any future structural evolution must publish V4 instead of modifying V1, V2 or V3.

`/api/proofpack/schema.json` is a discovery envelope. Its embedded schema has no `$id` and is an exact `oneOf` over the immutable V1, V2 and V3 schema URLs. The envelope also publishes the SHA-256 of every versioned schema.

Node and browser verification use the same Ajv standalone validators generated directly from the frozen JSON schema files. The Master format selects the validator. Absence of `formatVersion` selects only the historical V1 compatibility path.

The browser loads only the standalone validator selected by `formatVersion`.
Historical validators therefore do not accumulate in the initial `/verify`
bundle as new ProofPack versions are published.

Public UTF-8 canonicalization vectors are available at `/canonicalization-vectors.json`. They cover LF, CRLF, CR, NFKC, bidi and control characters, surrounding spaces, preserved invisible format characters, French and non-Latin text. The build checks these vectors against the implementation.

Questionnaire source binding validates both the canonical SHA-256 and the canonical UTF-8 byte size. A matching hash with a false `sourceQuestionnaire.size` is invalid.

Delivery V4 and V5 follow the same rule: their frozen schema files are compiled into separate Ajv standalone validators. Node and browser select the validator from `formatVersion` before Delivery link and business-invariant checks. V4 keeps the historical `/proofpack-delivery-schema.json` identifier; V5 introduces `/schemas/proofpack-delivery/v5.schema.json`. A shared valid/invalid Delivery corpus includes strict `date-time` cases, so a date-only `generatedAt` cannot be reported as schema-valid.

The generated modules contain no runtime `eval` or dynamic code generation. `pnpm schema:check` fails when either committed validator no longer matches its canonical schema.

A shared valid/invalid corpus is executed in Vitest and Chromium, including strict JSON Schema `date-time` cases without a timezone.


## Answer fields

Each ProofQuestion may contain answer editor fields:

- answerText
- answerReservation
- answerConfidence
- answerExportStatus

These fields are included in the ProofPack fingerprint.

Changing an answer must therefore change the ProofPack SHA-256 fingerprint.


## ZIP export

BLACKPROOF can generate a local ProofPack ZIP.

The ZIP is a delivery container.

It contains proofpack.json and derivative exports.

proofpack.json is checked through its own SHA-256 fingerprint.

manifest.json lists each payload file with its UTF-8 byte size and SHA-256, and carries a global manifest fingerprint over the canonical manifest fields and file entries. The local verifier accepts the ZIP directly and performs these comparisons automatically.


## Board memo

The Board Memo is exported as note-synthese.md.

It summarizes ProofDebt, evidence gaps, sensitive evidence handling, answer readiness and priority actions.

It is intended for decision support, not certification.
