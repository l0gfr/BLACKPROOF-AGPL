# BLACKPROOF — Security Model

## Security posture

BLACKPROOF is a high-security local-first cyber evidence product.

The engine must be treated as sensitive infrastructure because it processes:
- supplier cyber questionnaires;
- security evidence metadata;
- proof debt;
- reviewed ProofPack Delivery exports;
- future verification material.

## Non-negotiable principles

1. No document upload.
2. No network transmission of document content, evidence metadata, identifiers or fingerprints.
3. No trackers, no Google Fonts, no CDN-hosted runtime assets.
4. No untrusted HTML rendering.
5. No raw user-controlled content in Markdown headings.
6. No unsafe CSV export.
7. Cryptographic fingerprints must use standard cryptographic primitives.
8. Local-first does not mean careless local storage.
9. ProofPack integrity must never rely on non-cryptographic hashes.
10. Third-party exports must be fail-closed and whitelist-based: no implicit inclusion from the Master.
11. `do-not-export`, drafts, automatic suggestions and `not-exportable` evidence must be structurally absent from Delivery artifacts.
12. Internal evidence references must never be promoted into Delivery. Only the user-controlled `publicReference` may describe an external evidence item.
13. BLACKPROOF must never claim certification, legal conformity or regulatory guarantee.

## Input handling

All questionnaire input must be validated at the engine boundary.

Default limits:
- maximum questionnaire size;
- maximum number of questions;
- maximum line length;
- maximum case title length;
- maximum metadata field length.

Unsafe control characters and bidirectional override characters are stripped.

## Output handling

CSV exports must defend against formula injection.

Markdown exports must escape user-controlled text and avoid using user-controlled values as raw headings.

JSON exports are machine-readable and must be fingerprinted using canonical serialization.

## Cryptographic integrity

ProofPack fingerprints must use SHA-256 through Web Crypto.

The fingerprint lets a recipient check that the generated ProofPack payload matches the provided fingerprint.
It does not authenticate the author or the truth of declarations and is not a legal signature, certification, timestamping authority or qualified seal.

ProofPack schema validation uses an Ajv standalone module generated at build time from the canonical JSON Schema. The same generated validator runs in Node and the browser, without runtime code generation. Build checks reject schema/validator drift.

## Browser model

The app is browser-local only.

Allowed:
- local parsing;
- local scoring;
- local export generation;
- local verification.

Forbidden in this version:
- uploading questionnaires;
- uploading evidence;
- hidden telemetry;
- analytics trackers;
- Google Fonts or other remote font providers;
- public CDNs for runtime scripts, styles, fonts or images;
- third-party script injection;
- remote AI processing.

## Private server-log statistics

Operational audience statistics may be derived only from the Apache access logs
that already exist for delivery, security and diagnosis. The approved report:

- uses no browser tracker, cookie, pixel, beacon or third-party request;
- removes URL query strings before presentation;
- anonymizes IP addresses at GoAccess level 2;
- covers no more than the 14-day raw-log retention window;
- is available only below `/stats/` behind Apache Basic Auth;
- is marked `private, no-store` and `noindex, nofollow, noarchive`;
- is regenerated by a network-isolated, capability-free systemd oneshot.

GoAccess needs inline styles and script evaluation for its generated interface.
That exception must remain isolated to `/stats/` through a dedicated CSP. The
public application must retain its build-hash policy and must never inherit the
GoAccess `unsafe-inline` or `unsafe-eval` allowances.

## Compliance disclaimer

BLACKPROOF is a tool for structuring cyber evidence.

BLACKPROOF does not provide:
- NIS2 certification;
- ReCyF certification;
- ISO 27001 certification;
- legal advice;
- qualified audit;
- regulatory conformity guarantee.


## Local-first storage

BLACKPROOF may store local cases in IndexedDB.

This storage is browser-local and must remain no-upload.

Every new case, questionnaire import and restored dossier must require a
passphrase and persist its questionnaire, ProofPack and Delivery snapshots inside
an AES-GCM encrypted envelope. Restoration of a legacy clear backup must be
re-encrypted before it enters IndexedDB. The passphrase and decrypted content must
never be persisted as application state outside that envelope.

Historical clear-text records are redacted in the list and blocked at the storage
read boundary. Their exact case and snapshots must be migrated to encrypted
envelopes under a newly confirmed passphrase before the editor receives the
decrypted payload.

Encryption at rest does not hide the opaque record identifier, envelope version,
revision identifier, optional local label or timestamps. Do not use a sensitive
client name or secret as a local label. Encryption cannot protect an already unlocked page from a compromised
browser, extension or operating system. Downloaded artifacts and clipboard copies
are outside the IndexedDB security boundary.

BLACKPROOF must not store raw evidence binaries, passwords, API tokens, private keys or unredacted logs in V0.1.

IndexedDB schema version 12 removes the retired access-credential store and its
temporary metadata without deleting dossiers, encrypted snapshots or storage
epochs. Creating and reopening dossiers requires no account or application
server.

## Security audit gate

BLACKPROOF includes a static local audit:

    pnpm security:audit

The audit blocks common regressions:

- network egress primitives;
- silent telemetry primitives;
- third-party scripts;
- trackers and analytics SDKs;
- Google Fonts;
- public CDN domains;
- remote CSS imports, fonts and runtime assets;
- inline scripts;
- unsafe HTML injection;
- localStorage/sessionStorage usage outside the reviewed local-first storage layer;
- high-confidence private keys and provider credentials in tracked or otherwise
  versionable files.

This is not a replacement for a professional audit, but it is a mandatory regression gate.


## Production HTTPS invariant

BLACKPROOF must never serve the application or API contracts over plain HTTP.

Required production behavior:

- `http://blackproof.fr/*` returns a permanent redirect to `https://blackproof.fr/*`;
- `http://www.blackproof.fr/*` returns a permanent redirect to `https://www.blackproof.fr/*`;
- no static file, API contract, fallback route or asset is served before the redirect on port 80;
- HSTS is sent on HTTPS responses.

The production smoke test must fail if HTTP returns `200`.


## Production CSP invariant

BLACKPROOF production must send an enforced `Content-Security-Policy` header.

`Content-Security-Policy-Report-Only` alone is not acceptable in production.

Minimum enforced directives:

- `default-src 'self'`;
- `object-src 'none'`;
- `frame-ancestors 'none'`;
- `frame-src 'none'`;
- `form-action 'none'`;
- `connect-src 'none'`;
- `script-src-attr 'none'`;
- `upgrade-insecure-requests`.

`upgrade-insecure-requests` is added only when the build CSP is rendered into
the Apache production configuration. It is intentionally absent from Astro's
HTML CSP meta tag so the HTTP preview used by Playwright can load and hydrate
local `/_astro/` assets.

Inline execution policy:

- `script-src 'self' 'sha256-...'`;
- `style-src 'self' 'sha256-...'`.

Astro/Svelte hydration currently emits small inline scripts and an `astro-island` style block on client routes. BLACKPROOF permits these only through build-generated hashes, not through `unsafe-inline`.

The production smoke test must fail if the enforced CSP contains `unsafe-inline` or lacks `sha256-` hashes.


## Sensitive import handling

Questionnaire import is local-first and no-upload.

However, imported questionnaires may still contain sensitive information.

The case editor and personal Knowledge Vault clear their decrypted page state,
passphrases, previews and private signing material after 15 minutes without user
activity or one minute continuously in the background. They also expose an
immediate manual lock. A fresh passphrase is required before work can resume and
unsaved in-memory changes are not retained.

Users must avoid importing passwords, API keys, tokens, raw logs, unnecessary personal data or unredacted evidence.

BLACKPROOF provides a Panic Wipe action in `/app/cases` to clear BLACKPROOF-managed
cases and Delivery snapshots from the main IndexedDB database, and clears the
separate local knowledge vault.

The wipe also increments a persistent storage epoch. Writes from tabs opened under
an earlier epoch are rejected transactionally, while a browser broadcast
invalidates and clears sensitive state in open product views immediately. This
prevents a stale view from reconstructing storage after the wipe.

Panic Wipe cannot erase downloaded/exported files, clipboard history, screenshots,
printouts, browser or operating-system backups, proxy logs or copies already made
outside BLACKPROOF. It is not a remote wipe.
These limits are part of the user confirmation and must not be
presented as guaranteed device-wide erasure.


## Static, local-only application

No document-processing server, account endpoint or remote status registry is
part of this version. File inputs use local File APIs; input contents, derived
answers, keys and dossiers never leave the browser through application code.
The production CSP sets `connect-src 'none'` and `form-action 'none'`.
Workers, scripts and styles are self-hosted. Public API resources are static,
read-only JSON documents.

The source audit rejects networking primitives. Browser tests exercise import,
encryption and export while offline and verify that CSP rejects same-origin
and third-party network attempts. Keep archive limits, active-content
rejections, authenticated encryption, stale-tab guards and disclosure consent
boundaries when changing code.

Detached signatures prove possession of the signing key, not the identity of
its declared owner. Offline revocation statements are consistency checks only:
they do not prove an authenticated current status. The retired public registry
must return unavailable and must never be treated as active by default.

Product workflows are qualified on Chrome and Edge Desktop. Firefox, Safari
and mobile remain outside the support claim until equivalent cryptography,
IndexedDB, download, XLSX Worker and Panic Wipe coverage exists.
